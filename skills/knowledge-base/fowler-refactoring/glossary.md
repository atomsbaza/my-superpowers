# Glossary

**Code Smell** — A surface indication that usually corresponds to a deeper problem in the system. (Ch 3)
**Composing Methods** — Refactorings that focus on packaging code into well-named methods. (Ch 6)
**Feature Envy** — A code smell where a method seems more interested in a class other than the one it actually is in. (Ch 3)
**Primitive Obsession** — Using primitive data types (like integers and strings) to represent domain ideas (like currency or coordinates). (Ch 3, Ch 8)
**Refactoring** — A change made to the internal structure of software to make it easier to understand and cheaper to modify without changing its observable behavior. (Ch 2)
**Rule of Three** — A rule of thumb to decide when to refactor duplicated code: wait until you see the duplication for the third time. (Ch 2)
**Self-Testing Code** — Code backed by a suite of automated tests that can determine whether the code is functioning correctly. (Ch 4)
**Technical Debt** — The implied cost of additional rework caused by choosing an easy solution now instead of using a better approach that would take longer. (Ch 2)
**The Two Hats** — A metaphor for the two distinct modes of software development: adding functionality (changing behavior) and refactoring (changing structure). (Ch 2)\n
