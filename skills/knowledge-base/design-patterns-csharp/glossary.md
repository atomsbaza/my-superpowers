# Glossary

**Abstract Factory** — provides an interface for creating families of related objects without specifying their concrete classes (Ch5)
**Adapter** — converts one interface into another interface a client expects, letting incompatible classes work together (Ch8)
**Aggregation vs. acquaintance** — GoF's distinction between owning another object with an identical lifetime (aggregation, diamond-arrow) and merely knowing of/using another object with no ownership (acquaintance/association, plain arrow) (Ch31)
**Anti-pattern** — a commonly-repeated response to a problem that looks like a solution but produces net-negative consequences (e.g. God class, Golden Hammer) (Ch28)
**Applicability** — one of GoF's standard per-pattern sections: the specific situations in which the pattern should be applied (throughout Canonical GoF Reference sections)
**Black-box reuse** — reuse via object composition; no internal details of the composed objects are visible to the reusing object, only their public interfaces (Ch31)
**Bridge** — decouples an abstraction from its implementation so both can vary independently (Ch12)
**Builder** — separates the construction of a complex object from its representation, using a Director + Builder pair (Ch3)
**Chain of Responsibility** — passes a request along a chain of handlers until one handles it; in modern C# this is ASP.NET Core middleware (Ch22)
**Class pattern vs. Object pattern** — GoF's own split: class patterns rely on inheritance (fixed at compile time), object patterns rely on composition (can change at runtime) — most patterns in this book are object patterns (Ch30)
**Class scope vs. object scope** — GoF's second classification axis: class-scoped patterns fix relationships between classes at compile time via inheritance; object-scoped patterns deal with relationships between objects that can change at run time (Ch31)
**Collaborations** — one of GoF's standard per-pattern sections, part of the Structure/Participants/Collaborations trio: describes how participants work together to carry out the pattern's responsibilities (Ch31)
**Command** — encapsulates a request as an object, enabling queuing, logging, and undo/redo (Ch17)
**Composite** — composes objects into tree structures to let clients treat individual objects and compositions uniformly (Ch11)
**Concrete Factory / Concrete Builder / Concrete Product** — GoF participant-role naming: the specific implementing class behind an abstract factory/builder/product interface (throughout)
**Consequences** — one of GoF's four essential pattern elements: the results and trade-offs of applying a pattern, especially its impact on flexibility, extensibility, portability, space, and time (Ch31)
**Decorator** — attaches additional responsibilities to an object dynamically, as a flexible alternative to subclassing (Ch7)
**Delegation** — a receiving object forwards an operation to a delegate object, passing itself along so the delegate can refer back to the original receiver; an extreme, maximally flexible form of composition (State, Strategy, and Visitor all depend on it) (Ch31)
**Director** — in Builder, the class that orchestrates the building steps in the correct order via a Builder interface (Ch3)
**Double dispatch** — the mechanism behind Visitor's `Accept`/`Visit` call pair: the operation that actually executes depends on both the visitor's type and the element's type, which single virtual-method dispatch alone cannot express (Ch13)
**External vs. internal iterator** — an external iterator is driven by the client (which calls `Next`/`IsDone` itself) and is more flexible; an internal iterator controls its own traversal and applies a client-supplied operation to each element, which is easier to use but weaker without closures (Ch18)
**"Favor object composition over class inheritance"** — GoF's second foundational principle: assemble behavior at run time from black-box objects rather than baking it into a compile-time class hierarchy, since inheritance breaks encapsulation by exposing a parent's implementation details (Ch31)
**Facade** — provides a unified, simplified interface to a set of interfaces in a subsystem (Ch9)
**Factory Method** — defines an interface for creating an object but lets subclasses decide which class to instantiate (Ch4)
**Flyweight** — uses sharing to support large numbers of fine-grained objects efficiently, splitting state into intrinsic (shared) and extrinsic (context-supplied) (Ch10)
**Four-eyes / GoF (Gang of Four)** — the four authors (Gamma, Helm, Johnson, Vlissides) of the original 1994 "Design Patterns" catalog that this book's 23 core chapters follow (throughout)
**Framework (vs. toolkit)** — a reusable design for a specific class of applications that dictates the application's architecture and calls your code (design reuse, inversion of control) — contrast Toolkit (Ch31)
**God class** — an anti-pattern where one class accumulates too many responsibilities, becoming a maintenance bottleneck (Ch28)
**Golden Hammer** — an anti-pattern of applying one familiar tool/pattern to every problem regardless of fit (Ch28)
**Hollywood Principle** — GoF's name (in Template Method) for the inverted control flow where the parent class calls the subclass's operations and never the reverse: "Don't call us, we'll call you." (Ch16)
**Intent** — one of GoF's four essential pattern elements: a short statement answering what the pattern does, its rationale, and the design issue or problem it addresses (Ch31)
**Intrinsic vs. extrinsic state (Flyweight)** — intrinsic state is stored inside the flyweight, independent of context, and therefore shareable; extrinsic state varies by context, cannot be shared, and must be supplied by the client at the point of use (Ch10)
**Interpreter** — given a language, defines a representation for its grammar and an interpreter to evaluate sentences in it (Ch23)
**Invoker / Receiver** — in Command, the Invoker triggers the command object, the Receiver performs the actual action (Ch17)
**Iterator** — provides a way to access elements of a collection sequentially without exposing its underlying representation (Ch18)
**Known Uses** — one of GoF's standard per-pattern sections: real 1994-era systems (ET++, InterViews, Smalltalk-80, Unidraw, Choices, etc.) that are already known to apply the pattern, offered as evidence the pattern is a genuine, proven design rather than a theoretical exercise (Ch31)
**Mediator** — defines an object that encapsulates how a set of objects interact, promoting loose coupling by preventing objects from referring to each other directly (Ch21)
**Memento** — captures and externalizes an object's internal state without violating encapsulation, so it can be restored later (Ch19)
**MVC (Model-View-Controller)** — separates an application into data (Model), presentation (View), and input-handling/coordination (Controller) (Ch26)
**Null Object** — provides a do-nothing object as a substitute for a null reference, removing the need for null checks (Ch25)
**Not-Invented-Here (NIH) syndrome** — an anti-pattern of avoiding well-tested existing solutions in favor of reinventing them internally (Ch28)
**Observer** — defines a one-to-many dependency so that when one object changes state, all its dependents are notified automatically (Ch14)
**Originator** — in Memento, the object whose state is saved/restored via Memento snapshots (Ch19)
**Parameterized types** — generics/templates; a third axis (alongside inheritance and composition) for varying behavior, by supplying an unspecified type as a parameter at the point of use — unlike composition, the bound type can't change at run time (Ch31)
**Participants** — one of GoF's standard per-pattern sections: the classes and/or objects participating in the pattern, and their responsibilities (throughout Canonical GoF Reference sections)
**"Program to an interface, not an implementation"** — GoF's first foundational principle: don't declare variables as instances of particular concrete classes; commit only to an interface defined by an abstract class, and instantiate concrete classes only through creational patterns (Ch31)
**Prototype** — creates new objects by copying an existing object (a prototype) rather than instantiating a class directly (Ch2)
**Proxy** — provides a surrogate/placeholder for another object to control access to it (Ch6)
**Push vs. pull model (Observer)** — push has the subject send observers detailed change data, which assumes the subject knows what observers need and hurts reusability; pull sends a bare notification and lets observers query for what they need, which is more decoupled but requires observers to do more work (Ch14)
**Simple Factory** — a common (non-GoF) idiom where a single method/class decides which concrete class to instantiate based on input; distinct from Factory Method, which uses subclassing (Ch24)
**Singleton** — ensures a class has only one instance and provides a global point of access to it (Ch1)
**State** — allows an object to alter its behavior when its internal state changes, appearing to change its class (Ch20)
**Strategy** — defines a family of interchangeable algorithms and lets the algorithm vary independently from clients that use it (Ch15)
**Template Method** — defines the skeleton of an algorithm in a base class, deferring some steps to subclasses without changing the algorithm's structure (Ch16)
**Toolkit** — a library of reusable classes providing general-purpose functionality without imposing an application architecture (code reuse, "you call it") — contrast Framework (Ch31)
**Visitor** — represents an operation to be performed on the elements of an object structure, letting you add new operations without changing the classes of the elements (Ch13)
**White-box reuse** — reuse via class inheritance; the internals of the parent class are visible to and can be relied upon by the subclass (Ch31)
**Wide vs. narrow interface (Memento)** — a Memento has two effective interfaces: a wide interface exposed only to its Originator (full read/write access to captured state) and a narrow interface exposed to the Caretaker (which can only pass the memento around, never inspect it) (Ch19)
