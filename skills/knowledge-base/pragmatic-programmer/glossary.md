# Glossary

**Algorithm speed (O() notation)** — estimating how an algorithm's resource use (time/memory) scales with input size, independent of hardware (Ch6)
**Blackboard system** — a coordination pattern where independent agents post/read facts to a shared space rather than communicating directly, useful for loosely-coupled complex systems (Ch5)
**Boiled frog** — the analogy that gradual, incremental degradation goes unnoticed until it's severe; a warning against passively tolerating slow project decay (Ch1)
**Broken Window Theory** — visible small defects (bad design, wrong decisions, poor code) left unfixed signal that nobody cares, accelerating further decay (Ch1)
**Circles and arrows** — the author's term for informal, ad-hoc diagramming notations that lack a real underlying model — useful for communication but not a substitute for a real specification (Ch7)
**Code generator** — a program that produces other code/artifacts (passive: run-once scaffolding; active: run repeatedly to stay in sync with a source model) (Ch3)
**Coincidental programming** — writing code that happens to work without understanding why, making it fragile to underlying changes ("Programming by Coincidence") (Ch6)
**Contract (Design by Contract)** — a formal agreement between a routine and its callers: preconditions, postconditions, and class invariants (Ch4)
**Debugging mindset** — treating debugging as a rigorous "fix the problem, not the blame" scientific process, not guesswork (Ch3)
**Domain language** — a small, purpose-built language (internal or external DSL) that lets you express a solution in the vocabulary of the problem domain (Ch2)
**DRY (Don't Repeat Yourself)** — every piece of knowledge must have a single, unambiguous, authoritative representation within a system (Ch2)
**Dead program tells no lies** — the principle that a crashed program is safer than one that continues in a corrupted state; crash early rather than mask the failure (Ch4)
**Evil Wizard** — code-generation wizards (in IDEs) that produce code the developer doesn't understand; dangerous if you can't maintain what was generated for you (Ch6)
**Estimating** — giving a scope-qualified, precision-matched answer (e.g., "about 4 weeks" not "23.2 days") derived from breaking work into known units (Ch2)
**Four "I"s of duplication (imposed, inadvertent, impatient, interdeveloper)** — Hunt & Thomas's taxonomy of why duplication happens, used to diagnose DRY violations (Ch2)
**Good-enough software** — software whose quality is a negotiated requirement like any other, involving users in trade-off decisions rather than pursuing unbounded perfection (Ch1)
**Knowledge portfolio** — treating your professional knowledge like a financial portfolio: invest regularly, diversify, manage risk, review and rebalance periodically (Ch1)
**Law of Demeter** — a routine should only talk to its immediate collaborators (arguments, its own fields, objects it creates) — not to objects obtained transitively through others — to reduce coupling (Ch5)
**Metaprogramming** — writing highly configurable/generic code driven by metadata rather than hardcoded logic, so behavior changes without recompiling code (Ch5)
**Orthogonality** — designing components so a change in one has no effect on unrelated others, reducing risk and increasing productivity (Ch2)
**Prototype** — a deliberately throwaway exploration used to reduce risk or uncertainty in an area, distinct from a Tracer Bullet, which is meant to become part of the final system (Ch2)
**Reversibility** — architecting decisions (vendor choices, platform, data format) so they can be undone later without disproportionate cost, since "there are no final decisions" (Ch2)
**Refactoring** — restructuring code's internal structure without changing its external behavior, done continuously rather than as a rare rescue effort (Ch6)
**Requirements pit** — the metaphor that gathering requirements is an investigative, iterative process of digging beneath what stakeholders initially say they want, not a one-time document handoff (Ch7)
**Rubber ducking** — explaining a problem out loud (even to an inanimate object) to force explicit, precise articulation that often reveals the bug (Ch3)
**Ruthless testing** — testing early, automatically, and thoroughly against explicit contracts rather than relegating testing to a late, separate phase (Ch8)
**Software entropy** — the tendency of a system's structure to decay over time in the absence of deliberate maintenance effort, mirroring the broken-window dynamic (Ch1)
**Specification trap** — the failure mode of trying to capture every requirement in a single exhaustive up-front document before any coding starts, rather than iterating (Ch7)
**Stone soup** — the analogy for driving a project forward by first showing a small compelling result, then recruiting others' investment/resources once momentum exists (Ch1)
**Temporal coupling** — hidden dependencies on the *order* or *timing* of events, which should be made explicit (e.g., via workflow/state models) rather than left implicit (Ch5)
**Tip (numbered)** — Hunt & Thomas's signature device: short, quotable, numbered maxims (e.g. Tip 33: "If it can't happen, use assertions to ensure that it won't") distilling each section's lesson (throughout)
**Tracer bullet** — a thin, end-to-end skeleton implementation built early, meant to be refined into the final system (unlike a prototype, which is thrown away) (Ch2)
**Ubiquitous automation** — always running builds, tests, and releases via scripted, repeatable processes rather than manual steps, to eliminate human error (Ch8)
