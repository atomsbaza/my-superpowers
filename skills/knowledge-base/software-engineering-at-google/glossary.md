# Glossary

**Artifact-based build** — A declarative build graph that describes outputs and dependencies (Ch 18).

**Attention set** — The people whose action is currently needed in a code review (Ch 19).

**Beyoncé Rule** — Important behavior must have a test in the common CI path (Ch 1, Ch 11).

**Blameless postmortem** — Incident analysis focused on system conditions and improvements rather than punishment (Ch 2).

**Bus factor** — The number of people who could be lost before a project becomes unable to operate safely (Ch 2).

**CaaS** — Managed compute infrastructure that runs workloads with standardized scheduling and isolation (Ch 25).

**Canonical source** — The maintained, authoritative place for guidance or facts (Ch 3, Ch 10).

**Change list (CL)** — A reviewable unit of source change (Ch 9, Ch 19).

**Continuous delivery** — Keeping software releasable through automation, isolation, and frequent validation (Ch 24).

**Continuous integration** — Automated validation of changes as they enter a shared codebase (Ch 23).

**Culprit finding** — Identifying the change most likely to have caused a CI failure (Ch 23).

**DAMP** — Descriptive And Meaningful Phrases; test clarity is preferred to abstraction for its own sake (Ch 12).

**Dependency contract** — The compatibility, support, and responsibility agreement between provider and consumer (Ch 21).

**Feature flag** — A runtime control that separates code deployment from behavior exposure (Ch 24).

**Fidelity** — How closely a test, fake, or environment represents the behavior that matters (Ch 13, Ch 14).

**GSM** — Goals/Signals/Metrics; a traceable method for choosing meaningful measurements (Ch 7).

**Hermetic** — Reproducible because inputs and dependencies are explicitly controlled (Ch 14, Ch 18, Ch 23).

**Hyrum’s Law** — With enough users, every observable behavior becomes a dependency (Ch 1, Ch 15, Ch 21).

**Implicit dependency** — Reliance on behavior or state that is not part of the declared contract (Ch 1, Ch 18).

**Large-Scale Change (LSC)** — A coordinated, tool-assisted change spanning many files or teams (Ch 22).

**MVS** — Minimum Version Selection; choose explicit minimum dependency versions and validate the graph (Ch 21).

**Monorepo** — A repository containing many projects or most of an organization’s source (Ch 16).

**One-Version Rule** — Reduce organizational complexity by supporting one current dependency version where practical (Ch 16, Ch 21).

**Presubmit** — Validation performed before a change is committed (Ch 9, Ch 20, Ch 23).

**Psychological safety** — Confidence that questions, disagreement, and mistakes can be expressed safely (Ch 2, Ch 3, Ch 4).

**Readability** — Google’s standardized code-quality mentorship and approval process (Ch 3, Ch 7, Ch 9).

**Release train** — A predictable cadence for shipping changes (Ch 24).

**Remote execution** — Running build actions on managed workers (Ch 18).

**Servant leadership** — Increasing team capability by providing context, direction, teaching, and support (Ch 5).

**Sharding** — Splitting a large change or test workload into bounded units (Ch 22, Ch 23).

**Signal** — Evidence that a desired goal has been achieved (Ch 7).

**Static analysis** — Source analysis performed without executing the program (Ch 20).

**System Under Test (SUT)** — The bounded system whose behavior a larger test evaluates (Ch 14).

**Test double** — A substitute for a real dependency in a test (Ch 13).

**Test scope** — The boundary of behavior and dependencies observed by a test (Ch 11, Ch 14).

**Tricorder** — Google’s platform for integrating static-analysis tools and feedback (Ch 20).

**Trunk-based development** — Frequent integration into a shared head with few long-lived branches (Ch 16, Ch 23).

**YAQS** — A scalable question-and-answer system that preserves organizational knowledge (Ch 3).
